# 核心信念

本文档定义 Mimir Boot 文档与工程体系背后的核心信念。

## 1. 仓库是记录系统

对智能体来说，看不到的知识就等于不存在。

因此：

- 重要约束不能只存在于聊天记录
- 关键设计不能只存在于口头共识
- 长期有效的决策应进入版本控制

这也是为什么我们把 `docs/` 视为正式工件，而不是附属材料。

## 2. 入口要短，细节要深链接

超长 `AGENTS.md` 很快会变成陈旧、重复、无法校验的说明书。

因此：

- 根 `AGENTS.md` 只保留入口、优先级、跳转地图
- 具体主题下沉到 `docs/` 和模块 README
- 智能体通过逐层导航获取上下文，而不是一次性吞下所有内容

## 3. 真实代码事实优先于抽象口号

设计文档必须能映射到仓库真实结构。

例如本仓库的文档应围绕这些事实组织：

- Maven 多模块
- `parent` / `bom` / `common` / `starters` 的职责分工
- Spring Boot Starter 交付模式
- GitHub Actions 发布与质量门禁

脱离这些事实的“通用最佳实践”价值有限。

## 4. 计划是一等公件

多文件变更、结构调整、能力演进不应只靠聊天临时推动，应形成计划、记录和技术债追踪。

## 5. 优先编码约束，而不是编码偏见

对于长期重复出现的工程要求，应尽量沉淀为：

- 构建配置
- linter / 测试 / CI 门禁
- 文档模板
- 目录约定

而不是每次靠人为重复提醒。

## 6. 向后兼容优先

本仓库是基础框架，很多使用方会把它当作平台依赖。

因此默认假设是：

- 配置语义尽量兼容
- 公共模型尽量稳定
- starter 默认行为不随意改变
- 破坏性调整必须显式说明并先计划

## 7. 模块应单一职责

如果一个模块同时承担太多角色，就会使文档、代码和维护责任一起模糊。

本仓库建议保持：

- `parent` 只处理构建与工程规则
- `bom` 只处理版本矩阵
- `common` 只处理通用规范与基础模型
- `starter` 只处理一个明确的运行时能力中心

## 8. 文档不是装饰，而是工程杠杆

高质量文档的作用不是“看起来专业”，而是降低以下成本：

- 新人理解成本
- 智能体上下文装载成本
- 变更影响分析成本
- 文档漂移定位成本

如果文档不能帮助做决策，它就需要重写或删除。
