# 文档治理

本文档定义 Mimir Boot 文档体系的维护规则，目标是减少文档漂移，让仓库文档长期保持“可导航、可链接、可维护”。

## 1. 文档分类

### 入口文档

- `AGENTS.md`
- `ARCHITECTURE.md`

要求：

- 简短
- 稳定
- 以跳转导航为主

### 设计文档

- `docs/design-docs/*`

要求：

- 记录长期有效原则
- 解释“为什么”

### 产品规格

- `docs/product-specs/*`

要求：

- 描述“对使用者来说提供了什么能力”
- 不深入实现细节

### 执行计划

- 活跃需求：`docs/active/{版本}/{需求}/plan.md`
- 归档需求：`docs/archive/{版本}/{需求}/plan.md`（部分历史版本保留原有嵌套目录）

要求：

- 记录阶段性任务、决策、状态
- 随执行推进更新

### 生成文档

- 当前仓库没有生成文档目录。未来如引入生成文档，需在 `docs/index.md` 登记真实产物路径。

要求：

- 尽量由脚本或半自动流程维护
- 人工改动应谨慎

以上分类的核心区别是：

- 入口文档负责导航
- 设计文档负责原则
- 产品规格负责使用方视角
- 执行计划负责阶段性推进
- 生成文档负责事实快照

## 2. 更新触发器

出现以下情况时，应同步更新文档：

- 新增或下线 starter
- 变更默认配置行为
- 变更公共模型或异常语义
- 新增发布、测试、质量门禁规则
- 调整模块边界或依赖方向

## 3. 新鲜度规则

文档应具备明确的新鲜度信号：

- 是否仍反映当前代码事实
- 是否仍有有效链接
- 是否已被更高层文档索引
- 是否仍属于当前模块职责

如果答案是否定的，应：

- 修正文档
- 标记过期
- 合并重写
- 或删除并在索引中移除引用

全局说明、模块 README 与产品能力文档维护当前终态：将变化直接整合到对应章节，不追加“某日复核发现”等过程记录。日期仅用于元数据；执行过程、验证时间与历史结论放入计划或发布记录。

保留 Java、Spring Boot、Spring Cloud 等核心技术基线和 README 版本徽章。普通依赖及 Maven 插件清单省略由 Dependabot 频繁升级的版本号，只维护名称与用途，具体版本以 POM 为准。接入示例中的必要制品版本、兼容性说明及历史验证证据保留。

仓库根 README 面向接入方，不直接引用技术债台账或 TD 编号。必要的接入限制在正文简述，并链接对应模块文档；内部问题跟踪通过文档索引和技术债台账维护。

## 4. 索引规则

- 每个目录应至少有一个入口索引或 README
- 新文档新增后，应在上层索引处可发现
- 根入口文档只做导航，不重复完整内容

## 5. 面向智能体的要求

优秀的文档要让智能体可以：

- 快速判断下一步该读哪里
- 明白哪些内容是权威来源
- 分辨长期约束与一次性任务

因此，应优先避免：

- 巨大无结构的单页文档
- 大量重复描述
- 没有目录关系的散乱文件

## 6. 推荐维护节奏

- 每次涉及结构性改动时同步更新相关文档
- 计划完成后同步头部状态、验收结论和上层索引；版本归档时统一迁移执行记录，并更新引用
- 定期清理失效链接、过期计划和不再适用的参考资料
