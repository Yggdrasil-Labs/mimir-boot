# 可靠性约束

本文档定义构建、发布与运行时能力的长期可靠性边界。可执行命令与失败处置分别见[测试规程](../engineering/testing.md)和[发布规程](../engineering/release.md)。

## 原则

- 可靠性优先于短期便利；默认行为应可预测，失败模式应清晰。
- 构建、发布和接入方消费链路必须可验证；一次成功不替代边界覆盖。
- `parent`、`bom`、发布 workflow 的变更影响所有下游使用方，属于高风险变更。

## 工程与发布边界

- Maven Wrapper 是首选构建入口；本地和 CI 的基础完整验收必须共享检查实现与判定规则。
- Java 子检查必须核验 Surefire、Failsafe 和 JaCoCo 产物，不能以命令退出成功替代报告完整性；具体命令与 Sonar 执行条件由测试规程维护。
- 发布由 GitHub Actions 与 Release Please 驱动；根 `pom.xml` 的 `revision` 是版本事实源，正式 Maven Central 发布必须满足 GPG 签名和公开制品验证。
- 瞬态发布失败优先重跑原 GitHub job；手动补偿必须显式选择外部副作用。公开制品未可用时阻断收尾，不默认重复上传。

## Sonar 质量基线

以下是沿用的仓库要求，不是远端项目当前配置已经核实的声明。新代码范围默认按相对上个发布版本的改动识别；每次验收应核对 Sonar 项目设置、对应 workflow 与本次分析报告。配置漂移必须说明并处理，不能据远端较宽松的设置静默降低仓库要求。

| New Code 指标 | 仓库要求 |
|---|---:|
| 可靠性、安全、可维护性评级 | A |
| 新代码覆盖率 | >= 80% |
| 新代码重复率 | <= 3% |
| 安全热点审查率 | 100% |

不得为通过门禁而降低阈值、扩大 `sonar.*.exclusions`、关闭规则或使用无理由抑制掩盖问题。Sonar 严重度是风险信号，不能覆盖公共 API、配置绑定、默认行为和其他兼容性约束；兼容修复应保留旧语义并提供迁移策略，暂不能移除的风险必须登记有 owner、目标版本、复查条件和证据的技术债。

## 模块设计边界

- Starter 应有可解释默认值、明确关闭开关和可理解的失败日志或异常，避免隐藏副作用。
- `common` 的公共模型语义必须稳定；破坏性变化先计划。
- `parent` 与 `bom` 的兼容性、构建和发布影响必须在变更前评估。

## 变更与文档

结构性变更至少核对：已有模块构建、Starter 默认行为、版本发布与消费方式，以及对应 README 和导航是否同步。文档无法让使用者或 Agent 判断模块职责、权威来源或计划状态，本身就是可靠性缺陷。

Sonar 的远程门禁仅在受控条件下运行，不能用本地 `verify` 代替；修复或处置后必须以同一变更输入的新远端分析和 Quality Gate 结果闭环。具体条件与 issue 处置见[测试规程](../engineering/testing.md)。未闭合风险与专项证据见[技术债台账](../active/tech-debt-tracker.md)。
