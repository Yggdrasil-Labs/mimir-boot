# 质量评分

本文档定义本仓库当前采用的质量观察维度，用于帮助开发者和智能体判断哪些区域需要优先补强。

## 0. 使用边界

本文件是人工维护的"主观观察快照"，不是自动生成的质量报表。

在使用这份文档时，应同时注意：

- 它反映的是某个时间点的人工判断
- 它不能替代测试、CI、覆盖率和代码审查
- 如果没有及时更新，分数会快速失真

建议每次大版本演进、重要模块重构或文档体系显著变化后回看一次。

## 1. 评分对象

评分对象不是单纯的代码行数，而是"模块或文档在工程维度上的成熟度"。

## 2. 建议维度

每个维度可按 `A / B / C / D` 粗粒度打分：

| 维度 | 含义 |
|---|---|
| 正确性 | 行为是否稳定、是否有测试支撑 |
| 可读性 | 代码与文档是否容易导航和理解 |
| 可维护性 | 是否有清晰边界、低耦合、易扩展 |
| 文档完整性 | 是否有 README、索引、边界说明 |
| 发布成熟度 | 是否已纳入 CI、发布、版本策略 |

## 3. 当前观察

评估依据：当前 POM、模块与文档结构、已有验证记录和[技术债台账](./active/tech-debt-tracker.md)。受未解决问题影响的正确性、可维护性或发布成熟度标记为“待复核”；可读性和文档完整性按现有导航、README 与边界说明独立判断。
维护责任：进行结构性改动的人应同步校准本表，避免把过期印象保留下来。

| 区域 | 正确性 | 可读性 | 可维护性 | 文档完整性 | 发布成熟度 | 备注 |
|---|---|---|---|---|---|---|
| `mimir-boot-parent` | 待复核 | B | 待复核 | A- | 待复核 | 插件、profile 和消费边界有集中说明；TD-036 属性覆盖、TD-043 报告时序、TD-044 格式扫描仍未解决。 |
| `mimir-boot-bom` | 待复核 | B | 待复核 | A- | 待复核 | 版本集中管理，README 区分支持等级；TD-037、TD-040、TD-041 涉及消费者兼容性，坐标可解析不等于 API 可用。 |
| `mimir-boot-common` | 待复核 | B | B+ | B+ | 待复核 | 公共模型职责与校验入口有说明，已有定向回归；TD-042 分页绑定缺口仍影响直接消费路径。 |
| Starter 聚合模块 | 待复核 | B+ | 待复核 | A- | 待复核 | 10 个聚合子模块各有 README 与接入说明；TD-013/016/023、TD-038/039、TD-045/046 仍需兼容迁移或修复。 |
| `docs/` 文档体系 | B | A | B+ | A- | B+ | 入口、领域导航、计划状态和链接可核对；全局说明维护终态，版本发布记录仍待核对归档。 |

“待复核”表示对应维度的原评级不足以覆盖当前已知问题。恢复评级需满足技术债条目的验收标准：Parent 验证发布属性覆盖、最终覆盖率报告和格式门禁负向用例；BOM 验证受影响客户端的编译、初始化或启动；Common 与 Starter 验证相应绑定、脱敏、配置刷新及生命周期边界。文档评分只反映导航和已核对说明，不替代代码质量或远程发布验证。

## 4. 使用方式

当你准备发起改动时，可先问：

- 这个区域当前最弱的维度是什么？
- 本次改动是否应该顺手补齐文档、测试或边界说明？

## 5. 维护建议

- 每次大型演进后回看本评分
- 如果某区域长期停留在 `C` 或 `D`，应形成明确计划
- 不要为了"评分好看"而制造空文档，分数应反映真实可用性
- 如果无法给出明确依据，宁可把评分写成"待复核"，也不要伪装成确定事实
