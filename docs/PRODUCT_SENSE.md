## 这个产品是给谁用的？

Mimir Boot 的用户是 Yggdrasil-Labs 内部及外部的 Java 后端开发团队。他们需要一个稳定、可组合、按需引入的基础设施基座来统一技术栈、减少重复配置、沉淀通用能力。

## 产品原则

1. **接入体验优先** — 降低接入方的起步成本，而不是追求仓库内部一时方便
2. **稳定可预测** — 默认行为可解释、配置语义向后兼容、starter 不随意改变行为
3. **按需组合** — 每个 Starter 独立引入、独立关闭，不强制全家桶
4. **侵入性最低** — 自动装配方式对使用方代码侵入性低，可覆盖可关闭

## 决策优先级

1. 使用方稳定性与向后兼容（绝不妥协）
2. 接入路径清晰、默认可用
3. 功能完整性与可组合性
4. 内部工程便利

## 进入门槛

一个能力值得进入 Mimir Boot，应同时满足：

- 多项目可复用
- 接入路径明确
- 默认行为可解释
- 长期维护成本可接受

## 产品边界

Mimir Boot 不追求：

- 承担所有企业中间件能力
- 代替业务项目架构设计
- 在单个模块里解决所有问题

它做的是：定义基线、提供 Starter、沉淀通用约定。

| 阶段 | 文档位置 | 智能体的角色 |

| 执行计划 | `docs/active/{需求}/plan.md` | 按计划执行任务，更新进度 |

## 架构层不进入每功能流转（重要）

**以下文档是"长期架构约束"，不随单个功能迭代修改：**

| 长期约束文档 | 为什么不进流转 |
|---|---|
| `ARCHITECTURE.md` | 系统级边界、分层、依赖方向 |
| `docs/design-docs/core-beliefs.md` | 跨所有决策的工程信条 |
| `docs/SECURITY.md` / `docs/RELIABILITY.md` | 跨功能的长期约束 |

**规则：**

- 智能体在执行产品规格 / 设计文档 / 执行计划时，**只读**上述架构层文档，不修改
- 若发现必须动架构层约束，**暂停当前流转**，走独立的"架构 RFC"
- 架构层变更不能作为某次功能实现的副产物悄悄入库
